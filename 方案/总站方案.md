# Relay Panel 总站方案

> 文档状态：需求与实施方案，尚未开发。
>
> 本文中的路由、接口、页面和命令名称，除已明确标记为“现有能力”外，均为后续开发目标，不能直接在当前服务器执行。

## 1. 目标

当前每台 VPS 都各自运行一个 Relay Panel（以下简称 RP）。日常需要分别访问不同的 IP、端口或域名，管理不方便，也扩大了管理后台的公网暴露面。

总站的目标是建立一个唯一的管理入口：

```text
管理员浏览器
    -> 总站 admin.wakeup-ai.top
    -> 受控、加密的管理连接
    -> 各台子站 RP
    -> 各子站本机的 Xray、Nginx、线路、证书和数据
```

总站只负责管理、监控、升级和审计，不承载用户代理流量。因此，总站不会成为 Cloudflare、Reality 或其他线路的流量中转，也不应影响现有线路速度。

## 2. 名词与角色

| 名称 | 含义 |
| --- | --- |
| 总站 | 单独 VPS 上运行的 Relay Panel 总站模式，是唯一的日常管理入口。 |
| 子站 | 每台实际部署代理线路的 VPS，运行 Relay Panel 节点模式。 |
| 节点 | 总站登记的一台子站；“节点”仅用于管理通信，不等同于代理链路中的出口节点。 |
| 线路 | 子站 RP 内的 Cloudflare、Reality 等线路。线路的部署、有效期和分享仍归子站所有。 |
| 服务器有效期 | 总站对一台 VPS 的人工记录和提醒，用于提醒续费；不是线路有效期，也不是对子站的控制策略。 |
| 中央网关 | 总站对浏览器提供的受控访问层。它把管理请求发往指定子站，但不允许任意转发。 |

## 3. 不做的事情

- 总站不转发用户代理流量。
- 总站不替子站处理线路有效期、线路到期断连或线路续期；这些继续由子站自己的 RP 处理。
- 总站不因为“服务器有效期”到达而停用子站 Xray、Nginx 或线路。
- 子站 VPS 被服务商到期、关机或清空后，总站不尝试恢复它；总站只会检测到连接失败并提示。
- 总站不保存 SSH 密码，不提供网页终端，不允许执行任意 Shell 命令。
- 总站不把所有子站后台 IP、端口和 API Token 暴露给浏览器。

## 4. 推荐部署形态

### 4.1 总站 VPS

单独购买一台稳定的小型 VPS，安装 Relay Panel 的总站模式。总站不部署业务代理线路，主要运行：

- 总站 Web 页面和登录服务。
- 子站登记、状态采集和审计日志。
- mTLS 证书与受控管理凭据。
- 升级任务、备份状态和回退任务记录。
- 中央网关。

### 4.2 子站 VPS

每台业务 VPS 继续安装 Relay Panel 节点模式，继续本地拥有：

- Xray 与 Nginx。
- Cloudflare、Reality 等线路配置。
- 线路有效期、订阅、分享与诊断数据。
- 本机数据库、证书和配置。

子站需要升级到支持总站接入的最低版本。旧子站在首次接入前，需要用 SSH 手工升级一次；接入后才可由总站执行后续升级。

### 4.3 同一项目，不是两个不相干项目

总站与子站使用同一个 Relay Panel 项目和发布版本，但以不同角色运行：

```text
Relay Panel
    - central：总站模式
    - node：子站模式
```

为安全执行升级，子站可以额外运行一个无网页的受控升级组件。它不面向浏览器，只接受总站的 mTLS 请求，并且只允许固定的升级、回退和状态操作。

## 5. 总站域名与首次上线步骤

建议总站使用独立管理域名：

```text
admin.wakeup-ai.top
```

不要复用 Cloudflare 主线路、Reality 线路或订阅所使用的域名。总站域名只给管理员登录使用。

### 5.1 Cloudflare DNS

在 Cloudflare 为 `wakeup-ai.top` 添加记录：

| 字段 | 值 |
| --- | --- |
| 类型 | `A` |
| 名称 | `admin` |
| 内容 | 总站 VPS 的公网 IPv4 |
| 代理状态 | 橙色云朵，已代理 |

### 5.2 首次部署顺序

1. 购买总站 VPS，保留 SSH 密钥和服务商控制台作为紧急恢复方式。
2. 安装 Relay Panel 总站模式。
3. 初次通过总站 VPS 的临时管理地址登录，例如 `http://总站IP:2053/随机管理路径`。
4. 在 Cloudflare 创建 `admin.wakeup-ai.top` 的 DNS 记录。
5. 在 Cloudflare 生成 `admin.wakeup-ai.top` 的 Origin Certificate 和 Private Key。
6. 在总站初始化页面填写总站域名并上传 Origin Certificate 与 Private Key。
7. 点击“保存并应用”，总站自动生成 Nginx 配置并重载。
8. 使用 `https://admin.wakeup-ai.top/panel` 验证登录、页面资源和 API 正常。
9. 确认正式域名可用后，防火墙关闭公网对 `2053` 的访问，只保留 Nginx 本机转发。
10. 在 Cloudflare 将 SSL/TLS 设置为 `Full (strict)`，并为总站域名配置 Cloudflare Access。

### 5.3 正式访问路径

```text
浏览器
    -> https://admin.wakeup-ai.top/panel
    -> Cloudflare
    -> 总站 VPS 的 Nginx :443
    -> 总站本机 Relay Panel :2053
```

`2053` 可以继续作为总站程序本机监听端口，但不得继续对公网开放。

## 6. 安全模型

### 6.1 管理员到总站

- 管理员只访问 `admin.wakeup-ai.top`。
- Cloudflare 橙云隐藏总站源站 IP。
- Cloudflare Access 限制为管理员邮箱登录。
- RP 保留独立强密码；后续应增加二次验证。
- 不把总站原始管理端口暴露到公网。

### 6.2 总站到子站

- 总站与子站使用 HTTPS + mTLS 双向证书认证。
- 每台子站只信任总站签发的管理证书。
- 子站管理端口在 UFW 中仅允许总站固定公网 IP；后续可升级为 WireGuard 私网。
- 总站验证子站的 HTTPS 证书、主机名或证书指纹，不能跳过证书验证。
- API Token、私钥和 mTLS 密钥仅保存在服务端安全存储中，网页不回显明文。

推荐的后续私网形态：

```text
总站 WireGuard：10.10.0.1
子站 A：10.10.0.2
子站 B：10.10.0.3
```

启用 WireGuard 后，子站 RP 管理端口仅监听或仅允许私网地址访问。

### 6.3 受限接口原则

总站只能调用预定义操作，例如：

```text
读取服务器状态
读取线路列表和诊断
新建、编辑、应用、检测、删除线路
读取与重置 Clash 订阅
升级、回退、查看升级任务
```

不得提供：

```text
任意 URL 代理
任意文件读取
任意 Shell 命令
任意 SSH 终端
```

每次远程操作都记录：管理员、总站任务 ID、子站、线路、时间、参数摘要、结果和错误信息。

## 7. 总站首页

总站首页是服务器总目录，用于快速查看全部子站状态，不堆放每条线路的详细配置。

### 7.1 顶部汇总

显示四个汇总数：

```text
受管服务器
正常运行
运行异常
7 日内到期
```

### 7.2 服务器列表固定列

```text
状态灯 | 名称 | IP | 有效期 | 延迟 | 累计流量 | 版本 | 线路 | 异常
```

规则：

- 删除“状态”文字列；状态只通过最前方小灯表达。
- 删除“打开”列。
- 名称列每行只显示服务器名称，不显示地区、说明或第二行描述。
- 名称是链接；点击后在新标签页打开该子站的 RP 管理页面。
- IP 单独一列显示子站的管理地址。
- 有效期列使用两行格式，和现有 RP 线路有效期一致。

有效期显示示例：

```text
起：2026-08-01
止：2026-08-19
```

长期服务器显示：

```text
起：2026-08-01
止：长期
```

### 7.3 状态灯规则

| 灯色 | 条件 | 含义 |
| --- | --- | --- |
| 绿灯 | 总站连接正常，RP/Xray 正常，子站上报无技术健康异常 | 一切正常 |
| 黄灯 | 子站连接正常，且总站记录的服务器有效期不足 7 天 | 需要续费提醒 |
| 红灯 | 总站无法连接子站，或子站 RP/Xray 异常，或子站报告非“正常到期”的线路故障 | 需要处理 |

红灯优先级最高。子站中一条线路因为其自身“正常到期”而停止，由子站本地处理；总站不执行动作，也不将其当成必须修复的总站故障。

### 7.4 有效期的边界

服务器有效期是总站的人工提醒字段：

- 首次添加或编辑子站时由管理员填写。
- VPS 服务商的账单到期日无法从 Linux 或 RP 自动读取。
- 将来可对接 Vultr 等服务商 API 自动同步，但不是第一版范围。
- 到期或更新日期不会下发给子站。
- 到期不会停止子站线路、Xray、Nginx 或 RP。
- 子站被服务商到期关机或清空后，总站通过心跳失败自然显示红灯。

### 7.5 监控数值定义

- `延迟`：总站到子站 RP 管理接口的实际管理连通延迟，不是手机到代理入口的延迟。
- `累计流量`：子站内由 Relay Panel 管理线路的累计流量汇总，不使用服务器网卡的全部收发流量冒充线路流量。
- `线路`：子站当前保存的 Relay Panel 线路数量。
- `异常`：子站上报的、需要处理的线路或运行异常数量。

### 7.6 首页辅助区域

保留两个紧凑区域：

- 待处理事项：离线子站、技术异常、服务器有效期不足 7 天。
- 最近操作：部署、检测、有效期修改、升级、回退等操作的结果。

## 8. 点击名称后的子站 RP 页面

点击名称后，浏览器在新标签页打开：

```text
https://admin.wakeup-ai.top/servers/:serverId/panel
```

该页面在功能上是对应子站的 RP：它展示并操作该子站自己的线路、诊断、分享、Clash 订阅和线路有效期。

安全要求：

- 浏览器地址始终是总站域名，不出现子站 IP、端口或后台地址。
- 浏览器只登录总站，不能直接拿到子站 API Token。
- 总站根据 `serverId` 查找已登记子站，并通过受控接口读取或操作该子站。
- 不实现用户可输入任意 URL 的反向代理。
- 每个新标签页独立对应一台子站，允许同时打开多个子站查看。

实现时应优先复用现有 RP 的线路页面组件和交互，但数据请求由总站网关带上受控的子站标识，而不是让浏览器直接请求子站。

## 9. 子站接入流程

每台新子站都按照以下流程接入：

1. 购买并初始化子站 VPS，保存 SSH 密钥与服务商控制台恢复方式。
2. 安装或升级到支持总站接入的 Relay Panel 节点版本。
3. 确保子站 RP、Xray 和本机线路正常。
4. 在总站点击“添加服务器”。
5. 填写名称、IP/管理域名、端口、管理路径、服务器有效期提醒信息。
6. 总站执行一次 HTTPS 证书验证与连通性测试。
7. 为该子站建立 mTLS 信任关系。
8. 总站读取并记录节点身份、当前版本、Xray 状态和能力列表。
9. 总站确认子站支持的 Relay Panel API 版本和功能清单。
10. 在子站 UFW 中将管理端口限制为总站 IP，或改为仅允许 WireGuard 私网。
11. 从总站再次发起心跳检查，确认节点显示绿灯或黄灯。
12. 关闭日常对子站 RP 的公网直接访问，只保留 SSH/服务商控制台用于紧急恢复。

## 10. 子站管理 API 设计

需新增 Relay Panel 专用的节点管理 API。建议路径：

```text
/panel/api/central/v1/agent-info
/panel/api/central/v1/health
/panel/api/central/v1/lines
/panel/api/central/v1/diagnostics
/panel/api/central/v1/operations
/panel/api/central/v1/upgrade
/panel/api/central/v1/rollback
```

这些仅为设计路径，实际开发时必须定义版本化请求和响应结构。

接口要求：

- 仅接受总站 mTLS 证书和受控授权。
- 返回能力版本，避免总站向过旧子站发送不兼容操作。
- 所有写操作带幂等任务 ID，防止网络超时后重复部署或重复删除。
- 上传证书等请求保留大小限制、格式校验和审计记录。
- 返回结构化错误码与简短错误摘要，完整诊断留在子站日志。

## 11. 升级中心

总站单独提供：

```text
服务器 | 升级中心
```

服务器列表不放升级按钮，避免主表过宽和操作混乱。

### 11.1 升级中心显示内容

每台子站显示：

```text
名称
IP
当前版本
可选目标版本
最近可回退点
升级状态
```

### 11.2 指定版本升级

- 不强制升级到最新版本。
- 目标版本由管理员手动从已发布、已验证的 Git Tag 中选择。
- 未选择目标版本时，“开始升级”按钮不可用。
- 离线、版本过低或不满足兼容条件的子站不可加入升级任务。
- 同一次批量任务中的子站使用同一个目标版本；不同目标版本创建不同任务。

示例：

```text
美国住宅-A：v2.0.17 -> v2.0.18
美国 VPS-B：v2.0.14 -> v2.0.16
日本 VPS-C：保持 v2.0.15
```

### 11.3 单台升级

1. 在升级中心选择一台在线子站。
2. 从版本列表选择目标版本。
3. 查看版本跨度和兼容性提示。
4. 点击“开始升级”。
5. 页面实时显示任务阶段。
6. 完成后刷新版本、健康状态和可回退点。

### 11.4 批量升级

1. 勾选多台在线且兼容的子站。
2. 选择同一个目标版本。
3. 选择策略：默认逐台升级；可选每批两台或其他安全并发数。
4. 开始任务后，先升级第一台或第一批。
5. 每台完成健康检查后才处理下一台/下一批。
6. 任一台失败时暂停后续任务，明确显示失败服务器和错误原因。
7. 管理员可查看日志、重试失败节点，或结束任务。

### 11.5 每台升级的执行阶段

```text
等待
-> 备份当前版本
-> 下载并验证目标版本
-> 安装目标版本
-> 重启服务
-> 健康检查
-> 成功 / 失败并自动回退
```

健康检查至少包括：

- 服务进程已启动。
- 上报版本与目标版本一致。
- RP 管理 API 可访问。
- Xray 服务状态正常。
- 已有线路配置仍可读取。
- Nginx 配置测试通过。

### 11.6 回退

回退与“选择一个较低版本重新安装”必须区分：

| 操作 | 含义 |
| --- | --- |
| 指定版本升级 | 主动安装某个已发布版本，可以跨多个版本。 |
| 回退 | 恢复该子站一次升级前自动保存的程序、配置和数据库快照。 |

回退流程：

1. 升级前创建完整备份：程序、版本文件、服务文件、环境配置和数据库。
2. 新版本安装或健康检查失败时，子站自动恢复刚才的备份。
3. 成功升级后，升级中心显示该次升级对应的回退点。
4. 管理员点击“回退”时，先备份当前版本。
5. 恢复所选回退点，重启服务并执行健康检查。
6. 若回退失败，恢复回退前刚保存的当前状态。

当前本地 `relay-panel` 安装脚本已经具备“指定标签升级、升级前备份、失败自动恢复、最近备份回退”的基础。总站升级中心需要调用节点侧新的受控升级能力，而不是复用遗留 3x-ui 的“始终升级到最新版本”接口。

备份保留数量需要在实现时明确配置并在页面中展示。现有脚本默认保留两个旧备份；总站不得显示已经被清理的回退点。

### 11.7 总站自身升级

总站应最后升级：

1. 先升级并验证所有子站。
2. 确认子站管理和回退机制正常。
3. 升级总站自身。
4. 总站页面重启期间浏览器会短暂断开。
5. 重新打开总站后读取总站自身升级任务最终结果。

## 12. 现有 3x-ui 多节点代码的复用边界

Relay Panel 当前代码来自 3x-ui，已经存在节点登记、心跳、延迟、版本、Xray 状态、流量同步、HTTPS 校验和 mTLS 的基础能力。

可复用：

- 节点地址和 TLS 配置校验。
- HTTP 客户端、超时、证书校验、响应大小限制。
- 心跳、在线/离线、版本、资源状态采集。
- mTLS 证书生成和客户端认证基础。
- 节点操作审计和状态展示模式。

不能直接作为总站业务启用：

- 旧 3x-ui 节点逻辑会同步远程入站、用户、流量和 IP，必要时还会重新下发入站配置。
- Relay Panel 子站必须继续独立拥有自己的线路、Nginx、证书和有效期。
- 因此总站应新增 Relay Panel 专用 `ManagedServer`/节点管理模块，并隔离旧的入站同步任务。

## 13. 实施阶段

### 阶段 0：代码与发布准备

1. 明确总站模式与子站模式的配置方式。
2. 设计数据库迁移、节点身份和能力版本。
3. 设计 API 合约、mTLS 证书轮换和错误码。
4. 为全部新增功能补充单元测试、接口测试和权限测试。

### 阶段 1：子站安全接入与只读状态

1. 新增子站登记、编辑、删除和连通性测试。
2. 新增服务器有效期提醒字段，仅在总站保存。
3. 新增心跳、版本、管理延迟、Xray 状态和累计线路流量汇总。
4. 新增总站服务器列表和绿/黄/红状态灯。
5. 不开放远程线路写操作。

### 阶段 2：总站首页与子站页面

1. 完成首页汇总、待处理事项和最近操作。
2. 名称在新标签页打开 `servers/:serverId/panel`。
3. 通过总站网关读取指定子站线路、详情和诊断。
4. 保证浏览器不直接接触子站后台地址和凭据。

### 阶段 3：受控线路管理

1. 开放线路创建、编辑、保存并应用、检测、删除。
2. 开放分享、Clash 订阅查看与重置。
3. 所有远程写操作加入幂等 ID、超时、错误提示和审计日志。
4. 子站线路有效期仍只由子站本机逻辑负责。

### 阶段 4：升级中心与回退

1. 子站实现受控升级组件。
2. 总站读取可用发布版本和各节点回退点。
3. 实现单台指定版本升级。
4. 实现顺序/分批批量升级。
5. 实现失败自动回退和人工回退。
6. 完成升级任务日志、取消、暂停、重试和健康检查界面。

### 阶段 5：安全收口

1. 子站 UFW 仅允许总站 IP 或 WireGuard 私网。
2. 关闭子站 RP 日常公网直接访问。
3. 总站启用 Cloudflare Access。
4. 测试总站失联、子站失联、证书撤销、升级失败和服务商清空子站等恢复场景。

## 14. 发布与部署纪律

总站功能属于 Relay Panel 面向用户的正式功能。每次发布应执行：

1. 修改 `internal/config/version`。
2. 本地运行后端、前端和相关安全测试。
3. 提交并推送 GitHub `main`。
4. 等待 GitHub Actions CI 通过。
5. 创建并推送与内置版本完全一致的 `vX.Y.Z` Git Tag。
6. 先选择一台测试子站升级并验证。
7. 再通过总站逐台或分批升级其他子站。

不得在内置版本、Git Tag 或 CI 状态不一致时，把 `main` 宣称为可部署的新正式版本。

## 15. 验收清单

### 总站访问

- [ ] `admin.wakeup-ai.top/panel` 可通过 Cloudflare Access 登录。
- [ ] 浏览器不能直接通过公网访问总站 `2053`。
- [ ] Cloudflare SSL 模式为 Full (strict)。

### 子站接入

- [ ] 子站管理端口仅允许总站 IP 或 WireGuard 私网。
- [ ] 非总站客户端无法使用 API Token 或缺少 mTLS 证书访问节点管理接口。
- [ ] 总站能读取子站版本、Xray 状态、管理延迟、线路数量和累计线路流量。
- [ ] 子站离线时总站在合理心跳周期内亮红灯。

### 首页与页面跳转

- [ ] 首页列顺序为：状态灯、名称、IP、有效期、延迟、累计流量、版本、线路、异常。
- [ ] 没有“状态”文字列和“打开”列。
- [ ] 名称列没有多余第二行描述。
- [ ] 名称在新标签页打开对应子站 RP，地址仍为总站域名。
- [ ] 服务器有效期仅提醒，不影响子站线路。

### 升级与回退

- [ ] 升级中心可选择任意已发布、验证存在的目标版本。
- [ ] 目标版本未选择时不能提交升级任务。
- [ ] 单台升级、逐台批量升级和分批升级可用。
- [ ] 升级失败自动回退并保留可读错误信息。
- [ ] 人工回退恢复完整备份，并在失败时恢复回退前状态。
- [ ] 页面只显示实际存在的回退点。
